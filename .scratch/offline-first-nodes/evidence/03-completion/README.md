## Deterministic expiry: concrete seam blocker

No legitimate controllable bearer-verifier clock was found in the permitted workset. `idp_service::OAuth2Service::{verify_token_principal,validate_access_token}` use `Utc::now().timestamp()` internally; token issuance/exchange likewise use `Utc::now()`. Public `KeyService::load_node_signer(binding, issuer, now)` does accept a caller timestamp, but that only selects/loads the genuine signer at that time. Public `encode_jwt` can sign supplied claims, but changing signed exp/iat or swapping a token after authorization is not expiration of the same issued token across a response gate. Storage's own expiry checks use `SystemTime`. Paused Tokio time does not advance either owner clock. No IdP owner edit, forged claims, fake introspection, clock library/process-global override or sleep-based expiry proof was introduced.

To qualify the requested deterministic same-token expiry crossing, the IdP owner must expose/use a legitimate controllable current-time seam consistently in native bearer verification (and Storage must evaluate compatible time), or approve another genuine deterministic mechanism. This is a precise qualification blocker outside the assigned writes, **not a missing generic persistence API and not08**. Production expiry checks are already present; existing expired-token rejection is not substituted for this interleaving.
